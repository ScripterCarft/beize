# 0012 – Zeit: ntpd-rs mit NTS, Zeitzonen, Zertifikatsspeicher

Status: angenommen · 2026-10-09

## Kontext

Klassisches NTP ist nicht authentifiziert: Wer im Netz sitzt, kann die Uhr
verstellen und damit z. B. abgelaufene Zertifikate wieder gültig machen. NTS
(RFC 8915) sichert die Zeit per TLS ab; timesyncd kann das nicht. Beize zeigte
außerdem nur UTC (keine Zeitzonen-Daten), und im Dual-Boot hält Windows die
Hardware-Uhr in Ortszeit.

## Entscheidung

- **ntpd-rs** statt timesyncd (`-Dtimesyncd=false`): Rust (speichersicher, passt zu
  Beizes eigenem Code), NTS, Ubuntu 26.04 paketiert es. Gebaut nur mit
  dem System-OpenSSL – kein aws-lc, keine DNS-Bibliothek. chrony bräuchte für NTS
  GnuTLS mit fünf weiteren Bibliotheken. Releases: SSH-signierte Commits
  (`keys/ntpd-rs.allowed_signers`, `bz` prüft SSH-Signaturen dafür).
- **Server:** vier unabhängige NTS-Betreiber – PTB, Netnod, SIDN (time.nl),
  Cloudflare; mindestens drei müssen übereinstimmen. Die Liste steht allein in
  `/usr/lib/ntpd-rs/ntp.toml`; eigene Beize-Server später ändern nur diese Datei.
  `/etc/ntpd-rs/ntp.toml` ist ein Link darauf, den der Besitzer ersetzen kann.
  NTP-Server aus DHCP werden nicht genutzt (nicht authentifiziert).
- **Zertifikatsspeicher:** Mozillas Wurzelzertifikate (curls Auszug, gepinnt) unter
  `/usr/share/ca-certificates/`, verlinkt als `/etc/ssl/cert.pem` (OpenSSL) und
  `/etc/ssl/certs/ca-certificates.crt`. Gilt künftig für jedes TLS im System.
- **Zeitzonen:** tzdata (signiert, Paul Eggert); beize-setup fragt beim ersten Start
  nach Stadt oder Land und setzt `/etc/localtime`.
- **Hardware-Uhr in UTC** (systemd-Standard, keine Sommerzeit-Sprünge). Windows wird
  per `RealTimeIsUniversal` ebenfalls auf UTC gestellt; beim Start akzeptiert ntpd-rs
  jede Korrektur, falls die Uhr noch in Ortszeit steht.
- **Hardware-Uhr verloren (leere BIOS-Batterie):** `beize-save-clock.timer` merkt sich
  stündlich die von ntpd-rs **verifizierte** Zeit (mtime von
  `/var/lib/systemd/timesync/clock`, sonst schreibt das timesyncd); systemd stellt die
  Uhr beim Start mindestens darauf, mindestens aber auf `BUILD_EPOCH`. Eine falsche Uhr
  wird nie gespeichert. Die Uhr geht damit höchstens so weit nach, wie der Rechner ganz
  ohne Strom war (am Netz versorgt meist das Netzteil die Uhr).
- ntpd-rs startet nach einem Abbruch **nicht** automatisch neu (Upstream-Empfehlung:
  jeder Start erlaubt einen großen Sprung); der nächste Systemstart startet es.

## Konsequenzen

- `bz smoke` beantwortet die Zeitzonen-Frage (Land mit mehreren Zonen → Rückfrage)
  und verlangt die Zone bei jedem Start. Wie viele Server den NTS-Schlüsselaustausch
  geschafft haben (DNS, TLS, Zertifikate), wird berichtet, aber nicht verlangt
  (braucht Internet).
- ntpd-rs vertraut einer Quelle erst nach 8 Messungen im 16-s-Abstand: die Uhr gilt
  nach ~2 min als synchronisiert (in der VM gemessen). Bis dahin gilt die
  Hardware-Uhr. Schnelleres Abfragen belastet die öffentlichen Server und bleibt aus.
- `bz smoke` startet einmal mit Hardware-Uhr im Jahr 2000 (ohne kvmclock, das sonst
  die Host-Zeit liefert) und verlangt eine Uhr ab `BUILD_EPOCH`. Das Vorstellen auf die
  gespeicherte Zeit ist in der VM von Hand geprüft (Uhr zurückgestellt, Neustart).
- Restschwäche: War der Rechner länger ohne Strom, als die Server-Zertifikate alt sind
  (Wochen bis Monate), wirken sie „noch nicht gültig“ und NTS scheitert, bis die Uhr
  von Hand gestellt wird (`timedatectl set-time`). chrony löst das mit
  `nocerttimecheck` (Zeitprüfung beim ersten Schlüsselaustausch aussetzen, Kette und
  Name weiter prüfen); ntpd-rs kann das noch nicht – Kandidat für einen Upstream-Beitrag.
